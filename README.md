# Оптимизация процесса оформления заказа в E-commerce

## О проекте
Системный анализ и редизайн процесса оформления заказа для крупного интернет-магазина электроники с целью снижения уровня брошенных корзин и повышения конверсии без увеличения маркетингового бюджета.

## Проблема / Цель
**Проблема:** Высокий уровень отказов на этапе чекаута (75%). Из-за обязательной регистрации, скрытых платежей за доставку и медленной загрузки страницы оплаты компания теряла значительную долю выручки. На мобильных устройствах (70% трафика) показатель отказов достигал 82%.
**Цель:** Повысить конверсию из корзины в заказ (базовая: 25%) и улучшить мобильный UX, сохранив текущую архитектуру платформы.

## Контекст и ограничения
*   **Платформа:** Кастомная разработка (React + Node.js).
*   **Ограничения:** Бюджет ограничен, запрет на полную переделку сайта. Срок на MVP — 3 месяца. Платежные шлюзы (Stripe, PayPal, СБП) менять нельзя.
*   **Данные:** Доступна статистика воронки и API логистики для расчета доставки в реальном времени.

## 👤 Моя роль
Системный аналитик.
*   Провела валидацию исходных метрик и выявила математические несоответствия в воронке.
*   Смоделировала бизнес-процессы AS-IS и TO-BE.
*   Сформировала бэклог фич, провела приоритизацию.
*   Написала User Stories с Acceptance Criteria (Given-When-Then) и нефункциональные требования (NFR).

## Процесс и решения 
1.  **Анализ воронки:** Разложила 75% отказов по шагам. Выяснила, что 40% потерь приходится на шаг регистрации (10 полей, нет автозаполнения), 25% — на шаг доставки (скрытые платежи).
2.  **Приоритизация:** Использовала матрицу **Impact/Effort**. 
    *   *Quick Wins:* Прозрачная доставка (API уже есть), включение Apple Pay/СБП.
    *   *Big Bets:* Гостевой чекаут (исправляет 40% отказов, но требует доработки бэкенда).
    *   *Отложено:* One-page checkout (слишком высокая трудоемкость для MVP).
3.  **Компромиссы:** Защита от двойных списаний (Idempotency) вынесена в Must Have, так как это критично для лояльности и снижения нагрузки на поддержку, несмотря на то, что фича не дает прямого прироста конверсии.
4.  **Требования:** Декомпозировала фичи в User Stories. Для технических узлов (скорость загрузки, идемпотентность) прописала NFR.
